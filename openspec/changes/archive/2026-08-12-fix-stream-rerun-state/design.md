## Context

`BaseStream._compose()` turns `self._chain` (a list of `async def fn(iterable) -> AsyncGenerator` closures queued by intermediate ops) plus `self._stream` (the normalized source) into one executable pipeline. Two independent pieces of state currently outlive a single `_compose()` call in ways nothing accounts for:

1. `_sequential()` (`base_stream.py:34-41`) is given `self._chain` directly and calls `intermediaries.pop(0)` on it. Since Python passes the list by reference, this drains `self._chain` itself. A first `collect()` empties the chain; a second `collect()` on the same `Stream` instance then composes against an empty chain and just re-drains (or re-reads, if the source generator is also exhausted) whatever's left of `self._stream`.
2. `distinct()` and `limit()` (`stream.py:137-176`) each declare their mutable state (`seen = set()`, `size = 0`) in the *outer* function — the one that runs once, when `.distinct()`/`.limit()` is called — and close over it in `fn`, which runs once per composition. So the state is scoped to "this chain entry exists" rather than "this composition is running," and survives across separate `_compose()` calls that reuse the same `fn`.

`ParallelStream._parallel()` (`parallel_stream.py:18-43`) already avoids problem 1 for its own branches by passing `intermediaries[:]` (a shallow copy) into `_sequential()`, once per racing branch — so `self._chain` itself is untouched by a parallel `_compose()`. But `Stream._compose()` → `_sequential(self._chain, ...)` passes the live list, so `Stream` and `ParallelStream` currently honor different contracts for the same method. Problem 2 affects both subclasses identically, since both ultimately invoke the same `fn` closures.

This matters because `_compose()`/`sequential()`/`parallel()` are the seam every terminal op and every mode switch goes through — fixing it there fixes every call site at once, rather than patching individual terminal ops.

**How Java handles this, for comparison.** Java's `distinct()` and `limit()` are both stateful intermediate operations, and `java.util.stream`'s parallel implementation treats "stateful" as something the fork/join `Spliterator`/combiner machinery must reconcile, not something each parallel partition is free to do independently. For an **ordered** parallel stream, `distinct()` is documented as potentially costly precisely because it must merge each partition's view into one globally-correct, encounter-order-preserving dedup — never a partition-local dedup passed through unmerged. `limit(n)` on an ordered parallel stream is a known performance pitfall for the same reason: producing the *correct* first-`n`-by-encounter-order prefix can require nearly as much coordination as processing the whole stream. Only when the stream is `.unordered()` does Java relax this to allow cheaper, less-coordinated partition-local work — but the *result* is still globally correct (exactly n distinct/limited elements over the whole stream), never a merge of independently-capped partial results. Correctness is non-negotiable in Java's model; only cost varies with ordered vs. unordered.

This is the relevant precedent for Decision 3 below: snakestream's `ParallelStream` racing 4 branches each with their *own* `seen`/`size` would be the equivalent of Java silently producing a partition-local, un-reconciled result — a case Java's design explicitly avoids even in its cheapest (`unordered()`) mode.

## Goals / Non-Goals

**Goals:**
- Calling a terminal operation twice on the same `Stream`/`ParallelStream` instance produces the same result both times (assuming the underlying source is itself re-iterable — see Non-Goals), for chains with and without `distinct()`/`limit()`.
- `_sequential()` no longer mutates a list it does not own.
- `distinct()`/`limit()` closure state is scoped per-composition, not per-`fn`-object, for `Stream`.
- `ParallelStream`'s `distinct()`/`limit()` results stay globally correct across its racing branches within one composition — matching Java's guarantee that parallel execution changes cost, not correctness — rather than silently degrading into a per-branch-local, unreconciled result.

**Non-Goals:**
- Making `self._stream` itself re-iterable. If the source is a one-shot async generator (the common case — e.g. anything built from a Python generator or async generator), a second `_compose()` will still see it exhausted and yield nothing further. This change only guarantees the *chain* (closures + their state) stops being the reason a second run fails; sources that are inherently single-pass stay single-pass. This is worth calling out in regression tests so "second collect() returns []" isn't misread as unfixed.
- Changing the mutable-builder chaining semantics (`self._chain.append(fn); return self`) — that's the separate, larger "Later" roadmap item and is out of scope here.
- Making `limit()` a true short-circuit (`aclose()` before over-pulling) — separate roadmap item ("Next"). Note this is exactly the Java "ordered `limit()` is expensive" cost tradeoff playing out already in the codebase's TODO list, not something this change needs to resolve.
- Replacing `iscoroutinefunction()` dispatch — separate roadmap item ("Now", but independent).
- Adding Java's `unordered()`/ordered distinction to snakestream. Out of scope; `ParallelStream` has no ordering concept today (README/roadmap already tracks `unordered()` as a separate "Later" item), so this change preserves current (always effectively "ordered-correctness-required") semantics rather than introducing a cheaper unordered path.

## Decisions

**1. Fix `_sequential()` by copying, not by restructuring to iterative.**
Change `_compose()` to call `self._sequential(self._chain[:], self._stream)` (copy at the call site), leaving `_sequential()`'s recursive `pop(0)` structure untouched. Considered switching `_sequential()` to an iterative loop (also drops recursion depth == chain length stack frames), but that's a larger diff for the same outcome and not what's motivating this change — recursion depth matching chain length is not a reported problem. Copying at the one call site (`BaseStream._compose()`) is the minimal fix and makes `Stream` and `ParallelStream` consistent, since `ParallelStream._compose()` already does its own copying before calling `_sequential()`.

**2. Move `seen`/`size` inside `fn`, keyed by composition.**
For `distinct()`, change `seen = set()` from being created in `distinct()`'s body to being created at the top of `fn`'s body — but `fn` is `async def`, so a plain local re-initializes on every `fn(iterable)` call, i.e. every composition, which is exactly the desired granularity (once per `_compose()`, not once per element). Same for `limit()`'s `size = 0`. This is a pure relocation, no new data structures needed for the sequential case, because `fn(iterable)` (not the `async for` body) is the boundary that must own fresh state.

**3. `ParallelStream` shares one `seen`/`size` per composition across all its racing branches — explicitly, not by accident.**
`ParallelStream._parallel()` calls `self._sequential(intermediaries[:], iterable)` once per branch (`processes` times), each producing its own `fn(iterable)` call — so if `seen`/`size` simply moved inside `fn` per Decision 2 with no further change, each of the 4 branches would get an *independent* `seen`/`size`, silently changing parallel `distinct()`/`limit()` from "globally distinct/limited across branches" to "distinct/limited per-branch, then merged unreconciled" (e.g. `limit(2)` under 4 parallel branches could yield up to 8 elements before all branches individually hit their local `size >= max_size`; `distinct()` could yield the same value from two different branches since neither saw the other's `seen`). As established above, this is precisely the failure mode Java's parallel streams are designed to never exhibit, even in their cheapest mode — so it is rejected here on the same correctness grounds, not merely as a style preference.
   - **Chosen: keep current shared-across-branches semantics, made explicit.** `distinct()`/`limit()` closures accept their state (a `set`/counter wrapped in a small mutable holder) as an explicit argument threaded through composition, defaulting to a fresh holder when none is provided. `Stream._compose()` doesn't provide one (fresh holder per call, satisfying Decision 2). `ParallelStream._compose()`/`_parallel()` creates exactly one holder per composition and passes the same holder to all `processes` branches, so all branches read/write the same `seen`/`size` — reproducing today's (accidental) shared-state behavior, but now as a deliberate, tested contract instead of a side effect of closure scoping.
   - Rejected alternative: let state go fully per-branch-local and document parallel `distinct()`/`limit()` as approximate/best-effort. Rejected per the Java precedent above — Java never ships a parallel result that's merely "close" for these operations, and doing so here would be a **BREAKING**, unreviewed semantic change with no proposal-level sign-off, out of scope for a bug-fix change targeting "Now" roadmap items.
   - Rejected alternative: leave `ParallelStream` closure-state exactly as unowned module/instance state (today's status quo) and only fix `Stream`. Rejected because it leaves the two subclasses on divergent, undocumented mechanisms for the same guarantee, which is the exact inconsistency this change exists to remove.

## Risks / Trade-offs

- [Threading explicit state through closures for `ParallelStream` adds a parameter/holder object not present today] → Keep the holder internal to `distinct()`/`limit()`'s own machinery: it's created inside `_compose()`/`_parallel()` per composition (not at `.distinct()`/`.limit()` call time, which would reintroduce problem 2) and passed down only to the specific `fn`s that need it; other closures (`filter`, `map`, `sorted`, `peek`) are unaffected and keep their current signature. → Mitigated by scoping the change to exactly the two stateful ops, mirroring how Java scopes special combiner handling to stateful ops only.
- [Shared state across `ParallelStream` branches means `distinct()`/`limit()` still can't be embarrassingly parallel — same cost profile as before] → Accepted; this matches Java's own tradeoff (correctness first, cost second, for stateful ops) rather than being a regression introduced by this change. No behavior change for `ParallelStream` users, only a robustness fix (state no longer accidentally correct only because nobody re-ran the composition).
- [Non-Goal boundary is easy to misread as "still broken"] → A `Stream.of([1,2,3])` built from a `list` is safe to `collect()` twice today only by accident (lists re-normalize via `_normalize()` each time `_accept()`/construction runs — actually `self._stream` is fixed at `__init__` time as one `_normalize()` async generator, so even a list source is consumed after one full iteration). Regression tests must therefore assert "second `collect()` on a chain with `distinct()`/`limit()` doesn't crash and doesn't return stale/duplicated data," not "second `collect()` returns the same list" — the source exhausting itself is expected and out of scope. → Document this precisely in tasks/tests so the fix isn't judged against an impossible bar.
- [Recursive `_sequential()` still pops its own copy] → No behavior change from today for the copy itself (it was already fine within a single call); only the *aliasing* to `self._chain` is fixed. No new risk introduced.

## Migration Plan

No public API or signature changes for `filter`/`map`/`flat_map`/`sorted`/`peek`; `distinct()`/`limit()` keep their existing public signature (`() -> Stream`, `(max_size: int) -> Stream`). Internal-only changes to `_sequential()`, `_compose()`, `_parallel()`, and the two closures. No deprecation window needed; ship as a normal bug-fix release. No rollback complexity beyond a standard revert, since no data or external state is touched.

## Open Questions

- None outstanding — the one real fork (shared vs. per-branch `ParallelStream` state for `distinct()`/`limit()`) is resolved above in favor of preserving current shared-state behavior, backed by the Java precedent.
