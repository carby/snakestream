# Changelog

## What goes in here

This file is a **migration log**, not a release log. An entry exists so that a
caller upgrading between two versions can find out what they have to change, and
for no other reason. It is written for the person hitting the break, so each
entry says what changed, whether the break is **loud** (something raises) or
**silent** (code keeps running and does something different), and what to do
about it.

That scope means most of what a conventional changelog carries is deliberately
absent. New features are not listed here — the README's API tables are total over
Java 8's surface and are the place to learn what exists. Neither are performance
work, refactors, internal renames, or anything else a caller cannot observe.

So far, every entry is a **breaking change** — a rename, a removal, a changed
return type, a behaviour that used to be one thing and is now another. A handful
are marked `(not breaking)`: those are additions or fixes that a reader working
through this list would be misled by if they were missing, such as a new
exception type raised where nothing was raised before, or a behaviour that was
wrong and is now right. If you are upgrading and short on time, read the unmarked
entries and skip the marked ones.

Entries are newest first.

## Migration log

- **0.3.5 -> 1.0.0:** `collect(to_generator)` and `StreamingCollector` are removed from `snakestream.collector`. `to_generator` was a second spelling of `iterator()` — `collect(to_generator)` was implemented as `collector(self.iterator())`, adding a generator layer purely to re-yield what `iterator()` already produced, measured at +31% per element on a 200k-element `.map()` pipeline. `Stream.collect()` now accepts only a `Collector` or the three-argument supplier/accumulator/combiner form; its `StreamingCollector` overload and `isinstance` branch are gone, and passing anything else raises `StreamBuildException` naming `Collector`. **This break is loud**, with `ImportError` at the import site — `from snakestream.collector import to_generator` fails before any stream is built, and there is no shim. The replacement is `.iterator()`, or `async for x in stream:` for the common case, which needs no import at all and is faster. See `openspec/changes/remove-to-generator`.
- **0.3.5 -> 1.0.0:** `Stream.close()` on a handler whose result is awaitable now raises `StreamBuildException` instead of returning normally. Previously it called the handler, discarded the coroutine and returned as if the handler had run — the handler's body never executed at all, and the only trace was a `RuntimeWarning: coroutine ... was never awaited` surfacing later from a finalizer, far from the `close()` call site. `CloseHandler` was typed `Callable[[], None]` at the time, so an `async def` handler was never within the declared contract; it is now (`Callable[[], Awaitable[None] | None]`), and the closer that can complete one is `aclose()` or `async with`, which the exception message names. **The break is loud, and the behaviour it replaces was silent and did nothing** — a call site hitting it was already not releasing its resource. The refusal is an ordinary per-handler failure, not a special path: every remaining handler still runs, and the first failure in encounter order still propagates with the rest attached as notes. Separately and cosmetically, those notes read `also raised: {e!r}` rather than `close() also raised: {e!r}`, since `close()` and `aclose()` now share one failure tail. See `openspec/changes/archive/2026-09-09-async-close-handlers`.
- **0.3.5 -> 1.0.0 (not breaking):** `Stream(source)` no longer mis-normalizes a **falsy** `AsyncIterable`. `__init__` computed `_accept(source) or _normalize(source)`, and the `or` forced a truthiness test on the accepted source: an async iterable defining `__len__` returning 0 (or a falsy `__bool__`) fell through to `_normalize()`, whose final branch yielded **the object itself as a single element** rather than iterating it — silently, with no error and a wrong answer. The test is now an explicit `is not None` check. The same bug's loud face was `Stream(other_stream)`, which raised `TypeError` from `Stream.__bool__` (which raises by design) at construction; a `Stream` source is now unwrapped to `source.iterator()` and works, which additionally keeps an outer stream's source teardown from firing an inner stream's close handlers now that `Stream` has an `aclose()` for that teardown to probe for. One timing shift comes with it: `Stream(already_consumed_stream)` raises `IllegalStateException` at construction rather than at consumption. No working call site is affected — every one of these shapes either raised or produced a wrong answer before. See `openspec/changes/archive/2026-09-09-async-close-handlers`.
- **0.3.5 -> 1.0.0 (not breaking):** Keyword-spelled calls to `Stream.reduce()`, `reducing()` and `grouping_by()` now dispatch by **which** arguments were supplied rather than by the leading one, so a keyword spelling of any documented overload behaves identically to its positional spelling. Four call shapes that previously raised a confusing `TypeError` now work: `reducing(binary_operator=op)`, `reducing(identity=x, binary_operator=op)`, `reducing(x, binary_operator=op)` and `grouping_by(f, downstream=d)`. No positional call's behaviour changes. Separately, an argument set matching none of a function's documented overloads — a `combiner`/`mapper` supplied without an `identity`, `map_factory` supplied without `downstream`, or no accumulator/operator at all — now raises `StreamBuildException` at construction instead of failing later with a `TypeError` from an internal marker or a misdirected "downstream must be a Collector" message; no working call site is affected, since every one of those shapes already failed before this change. See `openspec/changes/split-arity-and-seed-sentinels`.
- **0.3.5 -> 1.0.0:** `collect(supplier, accumulator, combiner)`'s `combiner`, and every collector's `combiner` (`Collector(supplier, accumulator, combiner)`), start being invoked under `.parallel()` where the source spans more than one batch — see README's `Stream` and Collectors table rows and `parallel-reduction` (`openspec/specs/`). Fifteen built-in collectors gained one; `to_list()`, `to_set()`, `counting()`, `summing_int`/`summing_long`, `summarizing_int`/`summarizing_long`, `min_by`/`max_by`, `reducing()`, the two-argument `to_map()`, `joining()`, `to_collection()`, and `grouping_by`/`partitioning_by`/`mapping`/`collecting_and_then` where their downstream has one. `summing_double`, `summarizing_double`, all three `averaging_*`, and the three-argument `to_map()` remain permanently excluded (float accumulation is not associative; a caller-supplied merge is not required to be). `combiner` accepts either of Java's two conventions - mutate the first argument and return `None` (`list.extend`, matching Java's `Stream.collect(Supplier, BiConsumer, BiConsumer)`), or return the merged container (matching `Collector.combiner()`'s `BinaryOperator`) - so an existing `list.extend`-style combiner needs no change. **This is the one place an existing call site's result can change**: a caller who passed a **non-associative** `combiner` previously had it silently ignored under `.parallel()` and now gets a different answer - see `parallel-reduction`'s caller contract for what a combiner and an `identity` must satisfy. `.sequential()` is unaffected: a combiner is still never invoked there. See `openspec/changes/make-combiners-live`.
- **0.3.5 -> 1.0.0 (not breaking):** `Stream.reduce(identity, accumulator, combiner)` — the third of Java's three `reduce` overloads — is added. The existing `reduce(accumulator)` and `reduce(identity, accumulator)` overloads dispatch exactly as before; this adds a third arity, invoked the same way the 3-arg `collect()`'s combiner now is. See `openspec/changes/make-combiners-live`.
- **0.3.5 -> 1.0.0:** `RACING` is gone from `from snakestream.execution import RACING`; the import now raises `ImportError`. `.parallel()` no longer races `asyncio` tasks cooperatively over a shared generator on one thread — it dispatches contiguous batches of elements, decomposed by the new `spliterator()`, onto real OS threads via `asyncio.to_thread` (`_ForkJoin`/`FORK_JOIN`). Every documented guarantee (`.parallel()`'s API, encounter order under an ordered pipeline, `unordered()`'s relaxation, `.sequential()` as the remedy) is unchanged; only the mechanism underneath changed name. **This break is loud**, with `ImportError` at the import site — nobody outside `execution.py` had a reason to import `RACING` directly, since `.parallel()` is how a caller selects it. See `openspec/changes/archive/2026-09-04-fork-join-executor-and-spliterator`.
- **0.3.5 -> 1.0.0:** `PROCESSES` is renamed to `WORKERS`, in both `from snakestream import WORKERS` and `from snakestream.execution import WORKERS`; the old name now raises `ImportError` from either path. The rename reflects what the value has always actually been — the width of the pool `.parallel()` dispatches batches across — now that it names threads (`asyncio.to_thread` workers) rather than a name inherited from a process-pool design that was never built. The value is unchanged (4). **This break is loud**, with `ImportError` at the import site. See `openspec/changes/archive/2026-09-04-fork-join-executor-and-spliterator`.
- **0.3.5 -> 1.0.0:** `.parallel()` over a chain of cheap, non-blocking callables (no `await`, little per-element work — below roughly 1.4µs/element) now costs measurably more than it did, because dispatching a batch is a real `asyncio.to_thread` call now, not one more `asyncio` task cooperatively scheduled on the caller's own event loop the way the old racing executor did it. The regression scales with source size (roughly with the number of batch dispatches, `source size / BATCH_SIZE` at steady state) rather than staying flat — measured at ~4ms sequential vs. ~90ms parallel for 8192 elements of `x + 1` — and is specific to pipelines cheap enough that the old executor's per-element `asyncio` task overhead was already comparably expensive; work actually worth racing (I/O-bound callables, or CPU-bound work on the free-threaded build) is unaffected or measurably faster instead, up to 54x on I/O-bound work in the same benchmark. **This break is silent**: nothing raises, and the result is identical, only slower. `.sequential()` is the existing remedy for a pipeline where `.parallel()` was never buying anything. See `openspec/changes/archive/2026-09-04-fork-join-executor-and-spliterator`, `benchmark-findings.md`.
- **0.3.5 -> 1.0.0:** `requires-python` moves from `>=3.13` to `>=3.14`, the last of four sequenced floor raises - the supported set is now **3.14 only**. See `openspec/changes/archive/2026-09-04-raise-python-floor-to-311/proposal.md`, `…-to-312` and `…-to-313` for the earlier steps. Installing on Python 3.13 now fails at `pip` resolution rather than importing successfully and then working; this is loud, not a runtime failure. **This break has no silent part**, same as the 3.13 entry directly below and unlike the 3.12 entry two below it, whose alias-introspection change was silent and obscure - a reader upgrading straight from 3.10 can use that distinction to tell the four entries apart. Alongside it, 17 quoted forward references are unquoted (`"KeyComparator"` -> `KeyComparator` and similar, 13 of them in `comparator.py`), taking PEP 649's deferred annotation evaluation; verified by importing and exercising `comparator.py` specifically, since that module has no `from __future__ import annotations` and previously relied on the quotes rather than the future import. `from __future__ import annotations` itself is untouched everywhere it appears - removing it is a separate, non-trivial introspection change and was deliberately declined here. See `openspec/changes/raise-python-floor-to-314`.
- **0.3.5 -> 1.0.0:** `requires-python` moves from `>=3.12` to `>=3.13`, dropping the third of four floor raises taking the library to 3.14-only - see `openspec/changes/archive/2026-09-04-raise-python-floor-to-311/proposal.md` and `…-to-312` for the sequence and its destination. Installing on Python 3.12 now fails at `pip` resolution rather than importing successfully and then working; this is loud, not a runtime failure. **This break has no silent part** — unlike the 3.12 entry directly below, whose alias-introspection change was silent and obscure, this step's only observable effect is the loud resolution failure. Alongside it, `AsyncGenerator[T, None]` is respelled `AsyncGenerator[T]` at 14 sites, taking PEP 696's default for the send type parameter; both spellings denote the identical type, verified by `ty check` and `tests/test_static_typing.py`. See `openspec/changes/raise-python-floor-to-313`.
- **0.3.5 -> 1.0.0:** `requires-python` moves from `>=3.11` to `>=3.12`, dropping the second of four floor raises taking the library to 3.14-only - see `openspec/changes/archive/2026-09-04-raise-python-floor-to-311/proposal.md` for the destination. Installing on Python 3.11 now fails at `pip` resolution rather than importing successfully and then working; this is loud, not a runtime failure. Alongside it, `type.py`'s ~20 functional-interface aliases (`Mapper`, `Predicate`, `Comparator`, ...) and four generic classes (`Stream`, `StreamBuilder`, `Sink`, `Collector`) move to PEP 695 syntax (`type Mapper[T, R] = ...`, `class Stream[T]`), which 3.12 unlocks. **This break is silent and obscure**: an alias is now a `TypeAliasType` rather than a subscripted generic alias, so runtime introspection on it changes - `get_origin(Mapper[int, str])` moves from `collections.abc.Callable` to the alias object itself, and `get_args(...)` moves from `([int], str | Awaitable[str])` (the substituted structure) to `(int, str)` (the type arguments); the aliased type is now reachable only via `.__value__`. Static typing - the reason these aliases exist - is unaffected: `Stream[int].map(...)` still type-checks exactly as before, verified by `tests/test_static_typing.py`. Nobody is plausibly calling `get_args()` on one of these aliases, but every breaking change gets an entry regardless of how obscure. See `openspec/changes/raise-python-floor-to-312`.
- **0.3.5 -> 1.0.0:** `requires-python` moves from `>=3.10` to `>=3.11`, dropping the first of four floor raises taking the library to 3.14-only, in service of `spliterator()` on free-threading (PEP 779) - see `proposal.md` for the destination and why it is taken one minor version at a time. Installing on Python 3.10 now fails at `pip` resolution rather than importing successfully and then working; this is loud, not a runtime failure. Behaviour on every supported interpreter (3.11-3.14) is unchanged, `Stream.close()` included: on 3.10 `close()` previously raised the first handler's exception unmodified when more than one handler failed, since `BaseException.add_note()` did not exist there; that fallback path is deleted along with 3.10 support, and `close()` now always attaches the later exceptions as notes, which is what already happened on 3.11+. See `openspec/changes/raise-python-floor-to-311`.
- **0.3.5 -> 1.0.0:** `PROCESSES` is gone from `from snakestream import PROCESSES` and from `from snakestream.stream import PROCESSES`; both now raise `ImportError`. It was never a tunable lever - `execution.py` binds `RACING = _Racing(PROCESSES)` at import time, so assigning to the exported name after the fact changed nothing a pipeline did - and Java's `Stream` has no counterpart to be at parity with, since parallelism width lives in `ForkJoinPool.commonPool()`, never on the stream. The constant keeps its name and value in `snakestream.execution`, for a caller that was reading it for information rather than trying to set it. **This break is loud**, with `ImportError` at the import site. The number of racing branches remains an implementation detail; the supported levers for the cost of racing stay `.sequential()` and `.unordered()`. See `openspec/changes/archive/2026-09-03-name-by-visibility-not-underscore`.
- **0.3.5 -> 1.0.0 (not breaking):** A user-supplied `Comparator` that returns a non-`int` (a `bool` included) now raises `ComparatorContractException` (`snakestream.exception`) rather than a bare `TypeError`, from `sorted()`, `min()`, `max()`, `min_by()`, `max_by()` and a comparator segment alike. `except TypeError` is unaffected — the new type derives from it, following the `StreamException` base entry below — and `except StreamBuildException` / `except StreamException` now catch it too, alongside `_checked_segment_comparator`'s adjacent async-comparator-segment rejection, which already raised `StreamBuildException` and is unchanged. The one call shape that changes is exact-type matching, e.g. `type(e) is TypeError`, which no longer matches; the library has never promised the exact class, only that `except TypeError` catches. See `openspec/changes/add-comparator-contract-exception`.
- **0.3.5 -> 1.0.0:** `find_first()` no longer forces sequential execution, so it no longer overrides `unordered()` for the operations upstream of it. The element it returns is unchanged — still the first in encounter order, on ordered and unordered pipelines alike, because the racing executor's delivery barrier can restore encounter order on any chain (`unordered()` clears the *requirement* to honour it, never the ability). What changes is that an order-sensitive operation on an unordered chain now answers arbitrarily under `find_first()` as it already did under every other terminal: `.parallel().unordered().limit(8).find_first()` returns the leftmost element *of an arbitrary subset*, where it previously returned `source[0]` because `find_first()` silently made the whole pipeline sequential. This is the withdrawal of a suppression rather than new nondeterminism — `.unordered().limit(8).count()` has always been permitted to race — and it matches Java, whose `FindOp.mustFindFirst` is fixed at construction and whose `FindTask` scans leftmost *across* fork-join branches instead of falling back to a sequential traversal. **This break is silent.** Declare `.sequential()` to restore the old behaviour exactly. Note that the entry below, from an earlier release, describes `find_first()` as working "by driving under the sequential executor regardless of the stream's mode"; that mechanism is what this entry replaces, and the guarantee it describes still holds. See `openspec/changes/archive/2026-08-31-collapse-find-first-onto-barrier`.
- **0.3.5 -> 1.0.0:** A callable in a chain ending in `find_first()` may now be invoked for **more than one element** on a `parallel()` stream. A sequential `find_first()` pulls exactly one element and still does; a parallel one must have its branches racing before it can know which element is first, so it processes several — bounded by the worker count where elements complete at a uniform rate, and by the read-ahead window where the first element is slower than those behind it. Wall clock does not regress (a non-dropping head measures within noise of sequential, and a dropping one is ~3x faster), so the cost is work rather than time, and it is invisible unless the callable has side effects. Java's `FindTask` does the same speculative work in its leaves. **This break is silent**: a mapper that writes a row, increments a counter or logs will do so more than once. Declare `.sequential()` where exactly one invocation is required. See `openspec/changes/archive/2026-08-31-collapse-find-first-onto-barrier`.
- **0.3.5 -> 1.0.0:** `for_each_ordered()` no longer forces sequential execution on an ordered pipeline. It still invokes `consumer` in encounter order — that guarantee is unchanged — but it now obtains that order from the racing executor's delivery barrier rather than by discarding the stream's mode, so `.parallel().map(f).for_each_ordered(g)` races the `map` where it previously ran it one element at a time. **The break is that an operation queued *upstream* of the call is no longer invoked in encounter order.** A side effect in `peek()` or `map()` ahead of `for_each_ordered()` now fires concurrently and out of order; the same side effect placed *inside* `consumer` is ordered exactly as before. Java promises encounter order for the action alone and never for upstream stages — `ForEachOrderedTask` is itself a fork-join task, so Java's ordered path stays parallel too — which makes this a parity fix rather than a relaxation, but it is silent, and code relying on an ordered upstream counter or logger will see the same values in a different order with no error. Declare `.sequential()` to restore the old behaviour exactly. See `openspec/changes/archive/2026-08-31-collapse-for-each-ordered-onto-barrier`.
- **0.3.5 -> 1.0.0:** `to_map(key_mapper, value_mapper)` — the form called with no `merge_function` — now declares `Characteristics.UNORDERED`, so on an ordered `parallel()` pipeline it skips the delivery barrier it previously took. **The collected `dict` is unchanged**: keys and values each come from one element and consult no other, and `dict.__eq__` ignores key order, so the mark is truthful. Two things do change, both silently. The `dict`'s own **key iteration order** now follows the race rather than encounter order — `UNORDERED` promises equality and never promised iteration order, the same footing `to_set()` and `grouping_by()` already stood on, but a caller doing `next(iter(result))` or `list(result)[0]` under `.parallel()` gets a different answer. And with two or more **distinct** key collisions, which colliding key the `IllegalStateException` names is no longer guaranteed; that it raises at all is unchanged, since a duplicate key is a property of the elements and not of their order. The mark also propagates: `grouping_by(f, to_map(k, v))` and `mapping(f, to_map(k, v))` derive their characteristics from their downstream, so they skip the barrier now too. **`to_map(key_mapper, value_mapper, merge_function)` is unaffected and always will be** — a caller-supplied merge need not commute, so that form declares nothing and keeps its barrier. Sequential pipelines are unaffected in every case. See `openspec/changes/mark-to-map-order-blind`.
- **0.3.5 -> 1.0.0:** `bool(stream)` and every implicit truth test — `if stream:`, `not stream` — now raise `TypeError`. `Stream` previously defined no `__bool__`, so `object.__bool__` applied and **every** stream was truthy, an empty one included: `if stream:` answered a question the caller plainly meant to ask, answered it wrong, and said nothing. There is no correct synchronous answer to give instead, because whether a stream is empty can only be found by consuming it and consumption is asynchronous, so the refusal is the fix. **This break is loud** — a call site relying on the old always-`True` raises at the point of the mistake, and the message names the alternatives: `await stream.count()`, `await stream.any_match(...)`, `await stream.find_any()`. This is the only operation the library refuses that Python permits on other objects. Added alongside it, none of them breaking: `async for element in stream` (equivalent to iterating `stream.iterator()`), `with stream as s:` (equivalent to `contextlib.closing()`, which still works), `repr(stream)`, and `a + b` as sugar for `Stream.concat(a, b)`. See `openspec/changes/implement-python-data-model`.
- **0.3.5 -> 1.0.0:** A `Stream` subclass's `__init__` now runs **once per pipeline** instead of once per stage, and its attributes are shared across every stage by identity. Intermediate operations and mode switches derive the next stage by shallow-copying the receiver rather than calling `type(self)(source, close_handlers)`, which used to re-enter the constructor: `MyStream(src).map(f).filter(g).parallel().sorted()` ran it **five times**, and a resource acquired there was acquired five times while `close()` released the last. **This break is silent** and affects subclasses only — nothing raises, and code that counted acquisitions, or relied on each stage holding its own copy of a subclass attribute, now gets a different answer. It is in the safe direction: one resource per pipeline is what the documented use case always meant, and it is what makes the already-shared close-handler list coherent — registered once, released once. Two things become possible in exchange. A subclass may now define **any** `__init__` signature; nothing requires it to accept `(source, close_handlers)`, so `DsnStream(dsn)` acquiring a connection and calling `super().__init__(conn.rows())` works where it previously raised `TypeError` on the first intermediate operation — the shape README's own subclassing section describes. And a subclass's `__copy__`, previously inert, now governs derivation; `Stream` itself defines none, so the default shallow copy applies unless a subclass overrides it. See `openspec/changes/derive-without-reinit`.
- **0.3.5 -> 1.0.0:** `Stream.concat(a, b)` now **consumes both operands**, carries the execution mode of either, and is unordered if either is. Java's one sentence is the contract — the result "is ordered if both of the input streams are ordered, and parallel if either of the input streams is parallel" — and the concatenation previously honoured neither half: it returned a stream that was always sequential and always ordered, so `Stream.concat(a.parallel(), b.parallel()).is_parallel()` was `False`, and an `unordered()` declared on an operand was silently revoked past the concat, costing a caller the reorder barrier they had explicitly opted out of. Those two are **silent** widenings in the safe direction; operations queued onto the concatenation now race where Java would race them, and the mode stays overridable by a later `sequential()`/`parallel()`. The invalidation **breaks loudly**, with `IllegalStateException`: `c = Stream.concat(a, b)` followed by any operation on `a` or `b` now raises. It replaces a wrong answer rather than a lenient one — an operand and the concatenation draw on one source, so draining the operand afterwards returned its elements and left the concatenation yielding only the rest, with no exception anywhere (`[1, 2, 3]`, then `[4, 5]`). Java raises here too; `AbstractPipeline` marks the operands of `concat` linked. A caller who wants an operand's elements twice must build a second stream over the source. What the concatenation yields, when it pulls, and which close handlers it carries are all unchanged. See `openspec/changes/concat-carries-characteristics`.
- **0.3.5 -> 1.0.0:** `counting()`, `summing_int()`/`summing_long()` and `summarizing_int()`/`summarizing_long()` now declare `Characteristics.UNORDERED`, so on an ordered `parallel()` pipeline they skip the delivery barrier they previously took. **Nothing observable changes**: each returns a value that is identical under either delivery order — a count, an exact integer sum, or a `SummaryStatistics` whose every field is order-invariant over `int` inputs — which is why the mark is truthful. What changes is cost, and the reason it was worth making is that the barrier is not free on the work racing exists for: measured at 1.12-1.27x on IO whose latencies are skewed, where the uniform-latency benchmark that first deferred this had shown nothing at all. A caller wanting encounter-order delivery into these collectors for some other reason has `.sequential()`. The `summing_double()`/`averaging_*()`/`summarizing_double()` family is deliberately excluded and stays on the barrier. See `openspec/changes/mark-order-blind-collectors`.
- **0.3.5 -> 1.0.0:** On an ordered `parallel()` pipeline, `collect(grouping_by(f, d))` and `collect(partitioning_by(p, d))` with an order-blind `d` — `to_set()`, or anything else declaring `Characteristics.UNORDERED` — no longer deliver in encounter order. Both now derive `UNORDERED` from their downstream, by the same rule `mapping()` and `collecting_and_then()` already used, so they skip the delivery barrier where they previously took it. **This break is silent**: the collected value is unchanged under `==` — `dict.__eq__` ignores key order and each group's value is the downstream's, which by declaring `UNORDERED` promised equality under reordering — but the returned mapping's **key iteration order** is no longer deterministic where it previously followed encounter order. A caller relying on that order has three ways back: `.sequential()`, a downstream that observes order (the default `to_list()` does), or `sorted()` on the result's keys. They declined the derivation before on the ground that the returned dict's key order follows encounter order; that is true and is not what `UNORDERED` promises, which is equality of the result and nothing about how it iterates. See `openspec/changes/define-unordered-as-equality`.
- **0.3.5 -> 1.0.0:** `.parallel().max(c)` and `.min(c)` now break ties in **encounter order**. When two elements compare equal, the one earlier in the source wins, matching the sequential answer and Java's parallel `minBy`/`maxBy`; previously the winner was whichever the racing branches happened to finish first, which was arbitrary and unrepeatable. The *value* is unaffected whenever the comparator is consistent with equality — this changes only which of two equal-comparing but distinguishable records is returned, the shape you get from `comparing(lambda e: e.score)` over records with tied scores. **This break is silent** and in the safe direction: the answer is now the sequential one. In exchange these two terminals now take the delivery barrier on an ordered pipeline where they previously skipped it, which costs about 19% per element on a chain too cheap to race and nothing at all on work worth racing. `unordered()` restores both the old behaviour and the old cost exactly, and ties there are explicitly unspecified, as in Java; `comparing(k).then_comparing(t)` is the way to stay determinate without the barrier. `collect(min_by(c))` and `collect(max_by(c))` are **unchanged** — they already took the barrier, which is the divergence between the two forms this closes. See `openspec/changes/order-min-max-tie-breaks`.
- **0.3.5 -> 1.0.0:** An ordered `parallel()` pipeline now delivers its elements in **encounter order**. `.parallel().map(f).collect(to_list())` returns the mapped elements in source order where it previously returned them in whatever order the racing branches finished them, and the same goes for `reduce()`, `to_array()`, the three-argument `collect()`, `iterator()` and `collect(to_generator)`. Java's ordered parallel streams preserve encounter order into `collect`, so the scramble was the defect and the rule "racing does not preserve encounter order" is what went. **This break is silent** and in the safe direction: the answer is now the sequential one. A caller who wants the old behaviour declares `unordered()`, which is the documented lever, restores it exactly, and is measurably faster. Terminals that observe nothing about order — `count()`, `for_each()`, `find_any()`, `all_match()`/`any_match()`/`none_match()` — are unchanged and pay nothing (`max()`/`min()` were in this list when this entry was first written; see the tie-break entry below, which moved them out), as is any `collect()` whose collector declares `Characteristics.UNORDERED` (`to_set()` among the shipped ones). `find_first()` and `for_each_ordered()` are untouched. In exchange, an ordered pipeline behind a barrier *gains* concurrency in its suffix: `.parallel().limit(8).map(fetch)` now races the `map`, where it previously ran it one element at a time. See `openspec/changes/order-racing-delivery`.
- **0.3.5 -> 1.0.0:** `unordered()` no longer returns `self`. It now queues an operation onto the chain like every other intermediate operation, so it returns a **new** `Stream` and invalidates the receiver — the same derive-and-consume rule `map()`, `filter()` and the rest already follow. The fluent form `Stream.of(x).unordered().filter(...)` is unaffected; a caller that bound the receiver to a name and kept using it after calling `.unordered()` on it must use the returned instance instead, and **breaks loudly**, with `IllegalStateException`. Being an operation is also what makes it positional: `unordered()` now clears encounter order from its own position downstream instead of applying to the whole pipeline regardless of where it was written, and a later `sorted()` restores it, both matching Java, where `unordered()` is a `StatelessOp` contributing `NOT_ORDERED` and `sorted()` contributes `IS_ORDERED`. This is the deliberate opposite of `.parallel()`/`.sequential()`, which stay position-independent. See `openspec/changes/make-ordering-a-chain-characteristic`.
- **0.3.5 -> 1.0.0:** `is_ordered()` is gone from the public API, renamed to `_is_ordered()`. Java has no such accessor to be at parity with: `BaseStream` exposes exactly one piece of pipeline introspection, `isParallel()`, while the ordering characteristic lives in the package-private `StreamOpFlag.ORDERED` and is never readable by a caller — and there is no `ordered()` either, since ordering is a spliterator characteristic contributed by the source rather than something a caller turns on. **This break is loud**, with `AttributeError`, and there is no alias or deprecation period. Nothing about the ordering semantics changes: `unordered()` still clears the characteristic from its own position downstream, `sorted()` still restores it, and both still survive a `parallel()`/`sequential()` switch. A caller who was reading `is_ordered()` to decide something should express that decision through the pipeline instead — queue `unordered()` or `sorted()` and let the order-sensitive terminals (`for_each_ordered()`, `find_first()`) do what the characteristic says. See `openspec/changes/make-is-ordered-internal`.
- **0.3.5 -> 1.0.0:** `find_first()` no longer races like `find_any()` on a stream where `unordered()` is in effect; it returns the true first element in encounter order in every case, driving under the sequential executor regardless of the stream's mode and ordering. Java does not take the relaxation either — `FindOp.mustFindFirst` is fixed when the operation is constructed and `FindTask` does its leftmost scan whenever it is set, never consulting the upstream `ORDERED` flag, so the javadoc permits returning any element there but the implementation declines to. **This break is silent** and in the safe direction: the answer is now correct where it was previously arbitrary, most sharply on `.parallel().unordered().sorted(c).find_first()`, which returned a branch-local minimum rather than the smallest element. A caller who genuinely wants the race must use `find_any()`, which is unchanged. In exchange, `for_each_ordered()` now *gains* the relaxation Java gives it: on an unordered pipeline it runs under the stream's own executor instead of forcing sequential execution, matching `ForEachOps`' choice between `ForEachOrderedTask` and `ForEachTask`. See `openspec/changes/make-ordering-a-chain-characteristic`.
- **0.3.5 -> 1.0.0:** The collector factories move from `snakestream.collector` to a new `snakestream.collectors` module. `collector.py` had grown to 633 lines holding two unrelated things - the collector *protocol* and the ~20 collector *factories* - and Java already names that pair: `Collector` is the interface, `Collectors` the class holding the factories. The names that move: `to_list`, `to_set`, `to_collection`, `to_map`, `joining`, `counting`, `summing_int`, `summing_long`, `summing_double`, `averaging_int`, `averaging_long`, `averaging_double`, `summarizing_int`, `summarizing_long`, `summarizing_double`, `SummaryStatistics`, `min_by`, `max_by`, `reducing`, `grouping_by`, `partitioning_by`, `mapping`, `collecting_and_then`. Callers must update the import path: `from snakestream.collector import to_list` becomes `from snakestream.collectors import to_list`. **This breaks loudly** - `ImportError` at import time, before any stream is built - and no re-export shim is provided, so there is exactly one path to each name. **`Collector`, `StreamingCollector` and `to_generator` did not move** and stay in `snakestream.collector`: `to_generator` is a `StreamingCollector` instance rather than a factory, so it belongs beside the type it is an instance of, and the quickstart's `from snakestream.collector import to_generator` is unchanged. Nothing about any collector's behaviour, or about `collect()`, changes. See `openspec/changes/split-collector-protocol-and-factories`.
- **0.3.5 -> 1.0.0 (not breaking):** `StreamException` (`snakestream.exception`) is added as the base of both `StreamBuildException` and `IllegalStateException`, so `except StreamException` catches anything this library raised without enumerating the leaves. Inserting a base above two existing classes is source-compatible by construction: every existing `except StreamBuildException` / `except IllegalStateException` still catches exactly what it caught before. `StreamException` derives from `Exception` and nothing else - in particular not from `ValueError`, for the same reason `IllegalStateException` does not, stated in the entry below. It is never raised directly; it exists to be caught. Neither leaf is renamed and no third exception type is introduced. See `openspec/changes/split-collector-protocol-and-factories`.
- **0.3.5 -> 1.0.0:** `to_map(key_mapper, value_mapper)` now raises `IllegalStateException` (`snakestream.exception`) instead of `ValueError` when `key_mapper` produces the same key for two different elements. This matches Java, where `Collectors.toMap(keyMapper, valueMapper)` throws `IllegalStateException` on a duplicate key, and it reuses the exception this library already raises for reusing a consumed stream. `IllegalStateException` derives directly from `Exception`, **not** from `ValueError`: deriving it from `ValueError` would have kept existing call sites working, but the same class is what a stream-reuse error raises, and that is not a `ValueError` under any reading. So this **breaks loudly for `except ValueError`** around a two-argument `to_map` collection - the new exception propagates uncaught - and is invisible to a bare `except` or an `except Exception`. The three-argument `to_map(key_mapper, value_mapper, merge_function)` form never reached this path and needs no change; when, and on which key, the raise happens is unchanged, as is the message. See `openspec/changes/tidy-collector-containers`.
- **0.3.5 -> 1.0.0:** `.parallel()` and `.sequential()` now apply to the **whole pipeline**, regardless of where in the chain they appear, matching Java, where `parallel()` sets a flag on the pipeline's source stage rather than acting from that point onward. Previously they composed the chain-so-far into a generator and handed it to a new stream, which froze every operation declared *before* the call under the old mode: `.map(f).parallel()` ran `map` sequentially, while `.parallel().map(f)` raced it. Both now race it. A consequence worth stating on its own: there is no longer such a thing as a mid-chain mode switch — in `.parallel().map(f).sequential()`, the `.sequential()` wins and `map` runs sequentially. **This break is silent.** Results are unchanged; only which operations run raced changes, so nothing raises and no exception marks an unmigrated call site. A caller who deliberately placed `.parallel()` late to keep an earlier operation sequential must split the pipeline into two streams instead, collecting the sequential part and re-streaming it. `ParallelStream` is gone as a class — execution mode is now a value the stream carries — but it was never exported from `snakestream`, so no published name changes, and `.parallel()`, `.sequential()`, `is_parallel()` and `PROCESSES` all keep their names and meanings. One bug is fixed in passing: `.parallel()`/`.sequential()` were the only operations in the library that discarded a `Stream` subclass, returning a plain stream and dropping the subclass's attributes; they now preserve it, as every intermediate operation already did. See `openspec/changes/replace-parallel-stream-with-executor`.
- **0.3.5 -> 1.0.0:** `to_list` is now a factory, like every other collector in `collector.py` and like Java's `Collectors.toList()`. It was the one bare `Collector` instance in the public surface, so the API read `collect(to_list)` next to `collect(to_set())` for two equally stateless collectors. Callers must call it: `collect(to_list)` becomes `collect(to_list())`, and an explicit `grouping_by(f, to_list)` / `partitioning_by(p, to_list)` becomes `grouping_by(f, to_list())` / `partitioning_by(p, to_list())`. This breaks loudly, not silently: the bare name is a function, not a `Collector`, so an unmigrated call site raises `StreamBuildException` at the `collect()` call by the rule directly below. The collector's behaviour is unchanged, and the instance a single `to_list()` call returns is still safe to reuse across streams and concurrent collections - the factory shape is about one consistent rule for the public surface, not about state. See `openspec/changes/batch-small-cleanups`.
- **0.3.5 -> 1.0.0:** `Stream.concat(a, b)` is no longer a coroutine function. It is now an ordinary static method returning a `Stream` directly, matching the other static factories (`Stream.of()`, `Stream.empty()`, `Stream.builder()`, `Stream.iterate()`) and Java's static `Stream.concat`. Its body never awaited anything - concatenation is lazy by construction - so the `async` only forced callers into an `await` that could not suspend. Callers must drop it: `await Stream.concat(a, b)` becomes `Stream.concat(a, b)`. This breaks loudly, not silently: an unmigrated call site raises `TypeError: object Stream can't be used in 'await' expression`. What the concatenated stream yields, and when, is unchanged. See `openspec/changes/drop-async-on-concat`.
- **0.3.5 -> 1.0.0:** `Stream.collect(collector)` now requires a `Collector` (or `to_generator`, the one `StreamingCollector` exception), not an arbitrary `(composition) -> R` callable. Every collector this library ships (`to_list`, `joining`, `counting`, `summing_*`, `averaging_*`, `min_by`/`max_by`, `reducing`, `to_map`, `to_set`, `grouping_by`, `partitioning_by`) already returns a `Collector`, so calls using only those are unaffected. A hand-written callable collector must be rewritten as `Collector(supplier, accumulator, finisher=...)`, or wrapped in `StreamingCollector` if it is genuinely lazy/streaming. Passing anything else now raises `StreamBuildException` instead of being called as a function. See `openspec/changes/redesign-collector-shape`.
- **0.3.5 -> 1.0.0:** `grouping_by`/`partitioning_by`'s `downstream` argument now requires a `Collector`, for the same reason as above - every `collector.py` factory already satisfies this, so only a hand-written callable `downstream` needs converting. A consequence of the same change: each group/partition now accumulates into its own downstream container as elements arrive, rather than being buffered as a list and replayed through `downstream` in a post-pass once the source is exhausted. This is invisible for a pure downstream collector, but a downstream with side effects (e.g. `to_map`'s duplicate-key `ValueError`) now observes them interleaved with the source rather than after it. See `openspec/changes/redesign-collector-shape`.
- **0.3.5 -> 1.0.0:** The sync/async dispatch contract for every user-supplied callable (predicate, mapper, comparator, consumer, accumulator) invoked once per element narrows from per-result to per-callable-per-composition: whether a callable's results are awaited is now decided once at that callable's first invocation in a composition and held for the rest of that composition, instead of being re-checked on every result. A callable that returns an awaitable for some elements and a plain value for others - previously handled correctly - is no longer supported; its behavior is undefined. This has no Java analogue, since Java's functional interfaces cannot vary their return type per invocation. See `openspec/changes/optimize-callable-dispatch`.
- **0.3.5 -> 1.0.0:** `map()`, `filter()`, `flat_map()`, `sorted()`, `distinct()`, `peek()`, `limit()`, `skip()`, `sequential()`, and `parallel()` now return a **new** `Stream`/`ParallelStream` instance instead of mutating and returning `self`. Once a reference has been used to build a further instance this way (or has been terminally consumed), using that same old reference again for any of those ops, or for a terminal operation, raises a new `IllegalStateException` (`snakestream.exception`). This does not affect repeating a terminal operation on a reference that was never used to build a further instance (still supported, still returns an empty result on an exhausted source), nor `on_close()`/`close()`, which remain unaffected and continue to work on any reference regardless of this state. Callers relying on chaining off an intermediate result while continuing to build on the original reference must use the new reference returned by the op instead.
- **0.3.5 -> 1.0.0:** `StreamBuilder.build()` now returns a `Stream` over a snapshot of the builder's elements instead of a reference to its live internal list. `add()`/`accept()` calls made after `build()` no longer leak into the already-built stream.
- **0.3.5 -> 1.0.0:** `Stream.of()` no longer accepts keyword arguments. `Stream.of(a=1, b=2)` used to produce `[("a", 1), ("b", 2)]`; this had no Java equivalent and was undiscoverable from the signature. Callers must switch to `Stream.of(*some_dict.items())` for the equivalent stream of tuples.
- **0.3.5 -> 1.0.0:** `Stream.of("some string")` and `Stream.of(b"some bytes")` (and constructing a `Stream` from a `str`/`bytes` source generally) now yield a single scalar element instead of spreading into individual characters/bytes, matching how Java's `Stream.of(T...)` treats `String`/`byte[]` arguments atomically. Callers relying on the old char/byte-spreading behavior must switch to e.g. `Stream.of(*"some string")`.
- **0.3.5 -> 1.0.0:** `bytearray` and `memoryview` sources now yield a single scalar element instead of spreading into individual integers, joining `dict`/`str`/`bytes` in the scalar set. `Stream.of(bytearray(b"ab"))` used to produce `[97, 98]` and now produces the one `bytearray`; same for `memoryview`. This completes the entry directly above rather than extending it: `bytes` was already scalar, so the mutable buffer and the view over a buffer were spreading while the immutable buffer of the same data was not. **This break is silent** — results change, nothing raises. Callers relying on the old spreading behavior must switch to `Stream.of(*some_bytearray)`. A `memoryview` cast to a non-byte format spreads as that format's items under the old behavior and is scalar too under the new one; spread it explicitly if you want its items. See `openspec/changes/define-and-guard-stream-sources`.
- **0.3.5 -> 1.0.0:** `sorted()`/`min()`/`max()` now raise `TypeError` if the supplied comparator returns `bool` instead of `int`. Python's `bool` is a subclass of `int`, so a bool-returning comparator (e.g. `lambda x, y: x > y`) previously satisfied the `Comparator` type silently while violating its 3-way sign contract. Callers must switch to an int-returning comparator (e.g. `lambda x, y: x - y`).
- **0.3.5 -> 1.0.0:** `min()`/`max()` now require a Java-style 3-way comparator (negative/zero/positive int, matching `sorted()`), not a bool. Callers passing a bool-returning comparator (e.g. `lambda x, y: x > y`) must switch to one returning an int (e.g. `lambda x, y: x - y`) or their result will silently be wrong. This also fixes `min()`'s previous last-wins tie-break so it now keeps the first of equal elements, matching `max()`.
- **0.3.5 -> 1.0.0 (not breaking):** `comparing(key_extractor)` (`snakestream.comparator`) is added, matching Java's `Comparator.comparing(keyExtractor)`. It returns a `Comparator`, accepted anywhere one already is - `sorted()`, `min()`, `max()`, `min_by()`, `max_by()` - with no signature changes on any of them. `sorted()` recognizes it and extracts each element's key exactly once instead of once per comparison, which for an async key extractor is the difference between O(n) and O(n log n) awaits; every other comparator-consuming operation uses it as an ordinary `Comparator`. No existing comparator path changes. See `openspec/changes/add-comparator-comparing`.
- **0.3.5 -> 1.0.0 (not breaking):** `then_comparing()` and `reversed()` are added to the value `comparing()` returns, matching Java's `Comparator.thenComparing`/`Comparator.reversed`, letting a chain express a multi-key ordering with per-key direction (e.g. "department ascending, salary descending") and async key extractors, which a hand-written tuple key cannot. Sorting extracts every segment's key exactly once per element, concurrently across segments. No existing comparator path changes; every `comparing(f)` call with no chaining reaches exactly the code it reached before. The previously-private `_KeyComparator` (`snakestream.comparator`) is renamed to public `KeyComparator` so the chaining methods are visible to `ty`; it had no callers outside `comparator.py` and `sort.py`. See `openspec/changes/add-comparator-chaining`.
- **0.3.5 -> 1.0.0 (not breaking):** `nulls_first(comparator=None)` and `nulls_last(comparator=None)` (`snakestream.comparator`) are added, matching Java's `Comparator.nullsFirst`/`nullsLast`, so `sorted()`, `min()`, `max()`, `min_by()` and `max_by()` can be told where `None` goes instead of raising `TypeError`. They also tolerate a `None` *extracted key*, not only a `None` element - a case Java has no direct route to. Given a `KeyComparator`, the result keeps `sorted()`'s decorate-sort-undecorate fast path; given any other comparator, or none, the result is a plain wrapping comparator. Null tolerance is opt-in per comparator: every existing `comparing(f)` call, and every hand-written comparator, reaches exactly the code it reached before, and a stream containing `None` with no tolerant comparator still raises `TypeError`. See `openspec/changes/add-comparator-null-ordering`.
- **0.3.5 -> 1.0.0:** `Stream.__init__` drops its `close_handlers` parameter. `Stream(source)` is now the whole signature — `Stream(source, [handler])` raises `TypeError`. The parameter was a leftover of an internal calling convention `derive-without-reinit` (2026-08-31) already stopped using; `Stream.concat()` was its one remaining caller, and it now gets its operands' handlers through a named internal operation instead of through the constructor. **This break is loud**, unlike the silent one `make-stream-of-atomic` carried: it cannot be missed. Callers must switch from `Stream(source, [handler])` to `Stream(source).on_close(handler)` — `on_close()` is already the documented way to register a handler, mutates and returns the receiver, and is unchanged. A `Stream` subclass may still define any `__init__` signature it likes, which `derive-without-reinit` established and this does not narrow; only the base class's second positional parameter is gone. See `openspec/changes/inherit-context-on-concat`.
- **0.3.5 -> 1.0.0:** `Stream.of(*args)` is now atomic at every arity, matching Java's `of(T...)`. Every argument is one element, whatever it is: `Stream.of([1, 2])` used to spread the single list into two elements and now yields one element, the list itself; `Stream.of([1, 2], [3, 4])` was and remains a stream of two lists, since arity never spread a multi-argument call. **This break is silent** — results change, nothing raises. Callers relying on the old single-argument spreading behavior must switch from `Stream.of(x)` to `Stream(x)` for any iterable `x`; `Stream.iterate()` makes the same switch internally. See `openspec/changes/make-stream-of-atomic`.
